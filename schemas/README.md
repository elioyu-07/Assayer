# Assayer Data Schemas

These files use JSON Schema Draft 2020-12 to describe persistent audit entities and the rule registry. Relative `$ref` values are resolved from this directory.

## Files

- `common.schema.json`: shared types for IDs, timestamps, digests, rule references, result states, severities, coordinates, and source locations.
- `scan-run.schema.json`: input boundary, frozen rule set, status, and coverage proof for a Scan.
- `page-state.schema.json`: replayable page, dialog, drawer, tab, detail, and edit states.
- `entrypoint.schema.json`: processable, skipped, or pending page entrypoints in the Coverage Universe.
- `page-candidate.schema.json`: candidates discovered on a page but not yet promoted to formal AuditObjects.
- `object-verification.schema.json`: mechanical identity decision for Candidate promotion or AuditObject rebinding.
- `audit-object.schema.json`: audit objects discovered on real runtime pages.
- `operation.schema.json`: idempotent Host request execution and result-known state.
- `dimension-finding.schema.json`: immutable five-state Findings for object, frozen rule, and coverage dimension, including Evidence/Case references and supersession chain.
- `rule-assessment.schema.json`: fixed five-state decision for one object and one rule.
- `reverse-case.schema.json`: Agent-planned, Host-safely-executed reverse Case, including pre-action baseline, reverse actions, targeted recovery, verification, and refresh fallback.
- `action-attempt.schema.json`: Host safety decision, target, and request-observation references for one Case action.
- `request-observation.schema.json`: sanitized mechanical classification and sent state of an outbound request.
- The `recovery` structure is embedded in `reverse-case.schema.json`; a recovery adapter must provide `match/mismatch/unknown` checks for every required dimension.
- `evidence.schema.json`: immutable, sanitized Evidence generated by Host.
- `screenshot.schema.json`: object-focused screenshot and location status.
- `issue.schema.json`: formal issue derived from `issue_found`.
- `pending-decision.schema.json`: provisional decision created by `prepare_decision` before formal ledger commit.
- `rule-registry.schema.json`: extensible, versioned rule registry.
- `audit-ledger.schema.json`: aggregate audit ledger containing the entities above.
- `derived-issues.schema.json`, `page-element-judgement.schema.json`, and `run-diagnostics.schema.json`: publication contracts for read-only ledger-derived JSON.
- `runtime-event.schema.json`: sanitized runtime-event contract across Host, Agent, browser, Router, and diagnostic reports.
- `observability-manifest.schema.json`: event-stream integrity, extended-telemetry visibility, and diagnostic-completeness declaration.
- `performance-bill.schema.json`: wall-clock, Host, browser, transport, model-visibility, payload-size, screenshot, and duplicate-entrypoint measurements for one Scan.
- `public-progress.schema.json`: identifier-free, user-readable runtime phase, status, counts, and next-step contract returned by the product MCP facade.
- `plugin-manifest.schema.json`: domain-neutral plugin checks, evidence requirements, capabilities, and performance/recovery constraints.
- `platform-ledger.schema.json`: generic run operations, event timeline, commit receipts, and published artifact correlations.

The product runtime also exports the validated platform ledger as
`platform-ledger.json`, `platform-events.jsonl`, and `platform-run.log` in the
Scan output directory. The JSON file is canonical; JSONL is machine-oriented,
and the log is the human-readable chronological view.

The aggregate ledger described by `audit-ledger.schema.json` is the only runtime source of truth. Primary issue JSON, `page-element-judgement.json`, summary Markdown, and diagnostic Markdown must be derived deterministically and cannot modify the ledger. The current version does not generate HTML.

## Boundary Between JSON Schema and Host Semantic Validation

JSON Schema validates field types, enums, required properties, and local conditions, but cannot reliably express reference closure across arrays. Host therefore performs these semantic checks before committing:

1. Entity IDs are unique within the ledger and references target entities in the same Scan; Coverage Proof entrypoint references target `entrypoints`;
2. Every `scan.frozenRules` item exists in `ruleRegistry.rules`, with matching registry content;
3. Object, PageState, Case, Evidence, Screenshot, Assessment, and Issue references are closed;
4. `issue_found` references valid evidence for the current object and an independent `captured` screenshot whose object and PageState match;
5. `scanned_no_issue` requires the latest valid Finding for every required dimension to be `satisfied`; planned Case dimensions do not prove coverage;
6. Login failure or runtime interruption invalidates formal issue conclusions;
7. Rule IDs are never reused, semantic changes create a new version, and the registry snapshot remains frozen during a Scan;
8. If targeted Case recovery is `uncertain` or `failed`, a refresh-replay attempt follows; only final `restored` with every required check at `match` permits investigation to continue;
9. Operation `idempotencyKey` is unique within a Scan; repeated keys have identical request digests, and `result_unknown` cannot be replayed blindly;
10. Host semantic validation and a SQLite unique index jointly enforce one active `begin_case` per object-rule pair; actions reference real Cases;
11. `prepare_decision` creates only PendingDecision and any necessary IssueScreenshot, not Assessment/Issue; formal Assessment is committed only after the recovery barrier, and Issue has a one-to-one relation with an `issue_found` Assessment;
12. Derived views treat all Assessments and Issues in a `failed` Scan as invalid; `partial` retains only conclusions not covered by an invalidation event;
13. Identity, recovery, sanitization, and normalization algorithm versions match the versions frozen in the Scan;
14. Evidence/Screenshot binds only real PageStates and uniquely verified objects in the current Scan; a failed Raw Visual record cannot be used as a captured IssueScreenshot;
15. `complete_audit` partitions every entrypoint into exactly processed, skipped, or unprocessed, and Host recomputes rule summaries from formal Assessments; final `audit-ledger.json` passes the aggregate schema and is written atomically;
16. A Finding may supersede only the latest Finding for the same Scan, object, rule, and dimension. Superseded records remain but do not contribute to current coverage; Findings from unrecovered or recovery-invalidated Cases do not contribute to formal decisions.

## Digests and Normalization

- All JSON digests use UTF-8 and deterministic serialization: object keys are sorted and arrays preserve semantic order;
- Entity digests exclude their own digest field, random entity IDs, write timestamps, local paths, and other non-factual fields;
- Rule `contentDigest` hashes the rule file's original UTF-8 bytes;
- Registry `digest` hashes the normalized registry after removing the top-level `digest`;
- Screenshot digest hashes final immutable image bytes;
- See `docs/evidence-and-decision-integrity.md` for algorithm versions and design constraints.

## Boundary Between Protocol and Ledger

Protocol requests, responses, and PendingDecision are runtime interaction objects, not final ledger entities. Operation preserves idempotent execution facts. PendingDecision exists only until the commit transaction completes and does not enter the final formal ledger. Machine constraints for protocol envelopes are in `schemas/protocol/envelope.schema.json`; tool-specific input/output constraints are in `schemas/protocol/tool-contracts.schema.json`.

## Extension Rule

Adding a rule requires only a registry entry, rule document, and regression samples when existing Host capabilities are reused. A rule cannot add decision states or bypass evidence and screenshot gates.
